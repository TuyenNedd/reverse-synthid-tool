# SynthID detection and removal tool — review fixes (v2)

The fix commit addresses all seven issues from the v1 review: upload size enforcement on all three endpoints, mode-aware strength normalization with a `_normalize_strength` function, object URL revocation via `useRef` + `useEffect` cleanup, `asyncio.get_running_loop()` replacing the deprecated `get_event_loop()`, a threading lock around codebook cache writes, removal of the dead async client code, and documentation notes on the in-memory job store and `np.random.seed()` limitations.

Watch for: The codebook caching fix loads the codebook outside the lock, so multiple threads can still perform redundant (expensive) loads simultaneously on first access — they just won't corrupt the cache (likely). `ALLOWED_EXTENSIONS` is defined but never enforced — non-image uploads are only rejected when PIL fails to decode them (confirmed). The strength normalization logic is correct but has no dedicated test coverage (confirmed).

## High-level view

The strength normalization maps invalid strengths to `None` (engine default) rather than rejecting them, and the frontend gates options by mode with a reset on mode switch. The bidirectional mapping ("nuke" → "maximum" for fast, "aggressive"/"maximum" → "nuke" for full) means third-party API clients can send any reasonable strength for any mode without hitting the silent-fallback bug. No test exercises the normalization boundary cases.

The codebook cache uses double-checked locking with the expensive `cb.load()` call outside the lock. Multiple threads on a cold cache will each independently load the codebook; only the first writer's result is kept. The lifespan preload in `app.py` eliminates this in practice, but if the preload fails (file missing at startup), the redundant-load path activates.

`ALLOWED_EXTENSIONS` remains dead config — PIL's decode failure is the only guard against non-image uploads. Checking extension before `file.read()` would reject garbage without buffering it.

## Strength normalization boundary cases

The `_normalize_strength` function in `backend/routes/remove.py`:

```python
def _normalize_strength(mode: str, strength: Optional[str]) -> Optional[str]:
    if strength is None:
        return None
    s = strength.lower().strip()
    if mode == "fast":
        if s == "nuke":
            s = "maximum"
        return s if s in _VALID_STRENGTHS_FAST else None
    else:
        if s == "maximum" or s == "aggressive":
            s = "nuke"
        return s if s in _VALID_STRENGTHS_FULL else None
```

The existing test (`test_remove_sync_with_strength`) sends `"gentle"` and asserts `run_removal` receives it unchanged. What's missing: a test with `strength="nuke", mode="fast"` asserting `run_removal` receives `"maximum"`, and a test with an invalid strength asserting `run_removal` receives `None`. These are the cases the normalization was built to handle — the v1 bug's regression test.

## Codebook double-checked locking subtlety

```python
if _v3_codebook is not None and path is None:  # fast path, no lock
    return _v3_codebook

cb = SpectralCodebook()
cb.load(str(codebook_path))  # expensive I/O, outside lock

if path is None:
    with _cache_lock:
        if _v3_codebook is None:
            _v3_codebook = cb
        else:
            cb = _v3_codebook  # discard our load, use winner's
return cb
```

The race manifests only if the lifespan preload fails (codebook not found at startup) and the file appears later. In that scenario, N concurrent requests each load the codebook — wasting disk I/O and temporarily holding N copies in memory — but only one survives in the cache. A proper fix would acquire the lock before the `cb.load()` call, serializing cold-start loads.

## Upload validation gap

`ALLOWED_EXTENSIONS` in `config.py` is dead configuration. No route checks file extension or MIME type. The practical consequence: a user uploads a 40 MB ZIP file, the backend reads it entirely into memory, passes it to PIL, PIL raises, and the user gets a 400. The work (buffering 40 MB) was already done. Checking extension before `file.read()` would short-circuit without the allocation.
