# SynthID detection and removal tool with CLI, HTTP API, and React frontend

This is a greenfield project that wraps a research-grade SynthID watermark analysis codebase (detection via multi-scale spectral extractor, removal via frequency-domain codebook subtraction and a multi-stage V4 pipeline) into a distributable Python package with three access layers: a `detect`/`remove_fast`/`remove_full` library API, a Typer CLI, a FastAPI backend with async job processing, and a React+Vite frontend. The architecture separates the signal-processing engine (`_engine/`) from a typed public API (`detector.py`, `remover.py`, `codebook.py`) and then from the transport layers.

Watch for: The in-memory job store loses all state on restart with no cleanup of orphaned result files on disk (confirmed). The backend has no upload size enforcement despite configuring `MAX_UPLOAD_SIZE` (confirmed). The frontend's async removal path (`removeWatermarkAsync`) is wired in the client but unused by the UI, creating dead code alongside a potential object-URL memory leak (confirmed). Global mutable state in the codebook cache is not thread-safe under uvicorn workers (likely).

## High-level view

The core library exposes three entry points that translate numpy arrays into typed result dataclasses, lazy-importing the engine to stay importable without torch. Codebooks are cached at module level with no synchronization, which races under multi-worker deployments.

The backend mirrors the library's operations over HTTP, adding an async job layer backed by a dict-based in-memory store. Process restarts lose all job state and leave orphaned PNG files in `.results/`. The upload endpoints buffer entire files into memory without checking `MAX_UPLOAD_SIZE`.

The frontend uses the sync removal endpoint and renders before/after comparisons. The async job polling path is fully implemented in the API client but never called from any component, and the `JobStatus` TypeScript interface doesn't match the backend's actual response schema. Blob URLs for cleaned images are never revoked.

The strength dropdown sends "nuke" for both modes, but V3 bypass doesn't recognize "nuke" — it falls through to default (moderate) strength silently.

<summary>Issues (7)</summary>

1. **No upload size enforcement** — `MAX_UPLOAD_SIZE` is configured in `backend/config.py` but never referenced by any middleware or route handler. Clients can upload arbitrarily large files, risking memory exhaustion. Add a `Request` body-size limit middleware or check `content-length` in the route.
2. **Codebook cache not thread-safe** — `_v3_codebook` and `_v4_codebook` in `codebook.py` are global module-level variables mutated via `global` keyword. Under multiple uvicorn workers or threads, concurrent first-requests can race on the load-then-assign sequence. Use a threading lock or load codebooks exclusively in the lifespan handler.
3. **In-memory job store loses state on restart** — Completed job metadata and the association to result files on disk is lost when the process restarts, leaving orphaned PNGs in `.results/`. Document this limitation or add a periodic cleanup / persistence layer.
4. **Object URL memory leak in frontend** — `URL.createObjectURL(blob)` in `App.tsx` is never paired with `URL.revokeObjectURL`. Repeated removals accumulate Blobs in browser memory. Revoke the previous URL when creating a new one or on component unmount.
5. **Dead async removal path** — `removeWatermarkAsync` and `getJobResult` are exported from `api/client.ts` but never called from any component. Either remove them or wire the async flow into the UI (e.g. for full-mode removals that take longer).
6. **Strength mismatch between frontend and backend** — The frontend strength selector offers "nuke" but labels it "Maximum (Nuke)". When mode is "fast", "nuke" is not a valid strength for V3 bypass (valid: gentle/moderate/aggressive/maximum). The backend passes it through and the engine silently falls back to default. Gate the strength options by mode.
7. **`np.random.seed()` usage in engine** — `add_calibrated_noise` calls `np.random.seed()` which mutates global RNG state. Under concurrent requests this produces correlated outputs. Use a local `np.random.Generator` instance.

## Codebook cache race

The codebook module uses a global-variable caching pattern:

```python
_v3_codebook = None

def get_v3_codebook(path=None):
    global _v3_codebook
    if _v3_codebook is not None and path is None:
        return _v3_codebook
    ...
    if path is None:
        _v3_codebook = cb
    return cb
```

If two threads enter `get_v3_codebook` simultaneously when `_v3_codebook` is still None, both will load the codebook and one's assignment silently overwrites the other's. In the worst case both threads proceed with half-initialized instances during the overlap. Under the single-worker uvicorn configuration in `app.py` this won't trigger, but nothing prevents production deployment with multiple workers (gunicorn `--workers 4`). Confidence: **likely** — the race exists in the code; whether it triggers depends on deployment topology.

## Deprecated async API and result file leak

The async removal endpoint fires background work via:

```python
asyncio.get_event_loop().create_task(
    _process_removal(job.job_id, contents, mode, strength, model)
)
```

`asyncio.get_event_loop()` is deprecated since Python 3.10 and will raise in 3.12+ when no loop is running. Since this code always executes inside an async handler, `asyncio.get_running_loop().create_task(...)` is the correct replacement. Confidence: **confirmed**.

Result files written to `.results/{job_id}.png` are never cleaned up — no TTL, no cleanup on fetch, no background reaper. Over time this directory grows without bound. Confidence: **confirmed**.

## Upload size and file validation gap

`backend/config.py` defines `MAX_UPLOAD_SIZE` (50 MB) and `ALLOWED_EXTENSIONS`, but neither is referenced by any route or middleware. The `detect` and `remove` endpoints call `await file.read()` unconditionally, buffering the entire upload into memory. A 2 GB upload would be held in RAM until the request completes or fails. Confidence: **confirmed** — grep shows no usage of either constant outside `config.py`.

## Frontend object-URL lifecycle and dead code

In `App.tsx`:

```typescript
const url = URL.createObjectURL(blob);
setRemovalResult(url);
```

When the user triggers another removal, a new URL is created but the old one is never revoked. Each unreleased URL holds the full cleaned PNG in browser memory.

The API client exports `removeWatermarkAsync`, `getJobStatus`, and `getJobResult` but no component calls them. The `JobStatus` interface has fields (`created_at`, `completed_at`, `result_filename`) that don't match the backend's actual `JobStatusResponse` schema (`progress`, `error`), suggesting it was written against an earlier API design. Confidence: **confirmed**.

## Strength option mismatch across layers

The frontend's `RemovalPanel.tsx` offers a single strength dropdown regardless of mode:

```
gentle / moderate / aggressive / nuke
```

The V3 bypass engine maps strength via `{'gentle': 1, 'moderate': 2, 'aggressive': 3, 'maximum': 3}.get(strength, 2)`. "nuke" is not in this map, so it falls through to the default of 2 passes — equivalent to "moderate". The user selects "Maximum (Nuke)" expecting strongest removal but gets moderate. For "full" mode, V4 does accept "nuke". The frontend should filter strength options by mode or the backend should normalize before passing to the library. Confidence: **confirmed** — traced through `remover.py` → `bypass.bypass_v3()` → `get()` fallback.

## Test coverage gaps

Not tested:

- Integration test with a real codebook (detection accuracy).
- Concurrent requests to the async job endpoint.
- Job result download after actual background processing.
- Frontend has zero tests (no vitest/jest in `package.json`).
- `remove_full` happy-path (only a validation-error test exists; no mock equivalent).
- `bypass_v3` strength fallback behavior (the "nuke" bug would be caught).

## `np.random.seed()` global state mutation

`SynthIDBypass.add_calibrated_noise()` calls `np.random.seed(seed)`, which mutates the process-global legacy NumPy RNG. Under concurrent FastAPI requests (even single-worker async with `to_thread`), one request's seed can affect another's noise generation. The engine should use `np.random.default_rng(seed)` for isolation. Confidence: **confirmed** — line ~100 of `synthid_bypass.py`.
